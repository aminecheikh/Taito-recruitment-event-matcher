# MVP Implementation Plan — No CV, No Job Ad

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. On this repo, every "Ship" step means skill `ship` (check → named-file commit → `git pull --rebase` → push to `main`).

**Goal:** A Next.js prototype where one fictional applicant and one fictional company go through the whole event journey — core requirements → stories → AI-suggested links → signal → anonymous pick → shared card → both decide → information shared — on synthetic data, with switchable AI providers.

**Architecture:** One Next.js App Router app at repo root. Pure, immutable domain functions in `lib/domain/` operate on a single `Db` object; `lib/store/` persists it as a JSON file and serialises writes; screens call server actions that run `updateDb(fn)`. AI calls go through `lib/ai/` (Vercel AI SDK, provider from env, guardrails and mock fallback) exposed via route handlers with a per-visitor rate limit.

**Tech Stack:** Next.js (latest, App Router) · TypeScript · Tailwind · zod · Vitest · Vercel AI SDK (`ai`, `@ai-sdk/google`, `@ai-sdk/anthropic`, `@ai-sdk/openai`)

**Spec:** `docs/superpowers/specs/2026-11-14-mvp-design.md` (concept: `docs/pipeline.md`; rules: `AGENTS.md`)

## Global Constraints

- AI never scores, ranks, filters or rejects applicants; no percentage, "match", star or rank about an applicant anywhere. Only recruiters enter scores: integer 0–10 per core requirement.
- `MAX_CORE_REQUIREMENTS = 5`; a company has 1–5 core requirements.
- Before a meeting is `booked`, no screen and no server payload for recruiters contains `displayName` or `contact` — only `pseudonym` ("Applicant 017").
- AI text enters a story only after the applicant clicks accept, and then carries `languageLabel`: `"language edited"` or `` `translated from ${language}` ``.
- Every AI output in the UI is marked "AI suggestion" or "AI question"; on provider error or rate limit the UI shows "AI unavailable — showing example".
- An applicant can signal a company only with ≥ 1 accepted link to that company's core requirements; `signalsPerApplicant` default 3; `meetingSlots` default 10.
- Synthetic data only: ids like `talent-017`, `company-01`; company names end in `(fictional)`; emails only `@example.org`.
- Env: `AI_PROVIDER` = `google` | `anthropic` | `openai` | `mock` (default `mock`), `AI_MODEL`, `GOOGLE_GENERATIVE_AI_API_KEY`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `DB_PATH` (default `data/runtime/db.json`), `AI_RATE_LIMIT_PER_MINUTE` (default 10). Keys only in `.env`; agents never read `.env`.
- Immutability: domain functions return new objects; never mutate inputs.
- Visual: plain, readable, WCAG AA contrast, works at phone width; no purple/indigo gradients, icon-in-circle grids, glassmorphism or emoji decoration. No City of Espoo branding as product identity.
- Scoring guide text: none yet (open, two teammates researching) — score inputs only.

## Review Focus

1. **Two browser windows clicking at once** (presenter toggles recruiter and applicant) → both writes persist; no lost update, no half-written file. Test in Task 2.
2. **Model returns something off-spec** (unknown `requirementId`, two questions, "85% match" in a reason, invalid JSON) → output is filtered or replaced by the mock, never shown raw. Tests in Task 8.
3. **Recruiter changes core requirements after applicants linked and signalled** → cards and coverage use only current core requirements; links to a requirement that is no longer core are ignored, not counted. Test in Task 3.
4. **Name leaks through the payload, not the screen** → the card object sent to recruiter pages has no `displayName`/`contact` until booked, even if the UI doesn't render it. Test in Task 3.
5. **`db.json` missing, empty or corrupt at start** (first run, deleted, crash mid-write) → app reseeds from `data/synthetic/` with a console warning instead of crashing. Test in Task 2.
